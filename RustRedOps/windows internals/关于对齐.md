关于结构体在内存中的对齐,一个结构体在内存中如何对齐,取决于其内部最大字段的类型的大小.如裸指针在win64下是8字节的,其物理上天然就是8字节对齐

栈顶RSP指针是16字节对齐的.但call指令压入了一个8字节的返回地址,把栈搞成了8字节对齐.于是在函数的prologue中其第一句汇编指令是push register或sub rsp,0x28来修复为16字节对齐.

## movaps （SSE / XMM 16 字节死硬校验）

是所有手写汇编(如 uwd/desync.asm) 和 堆栈伪造中最容易触发程序直接闪退(0xC0000005或#GP)的坑

物理本质:win64 cpu引入了两条向量传输指令
1. movaps(move aligned packed(紧凑的) single-precision),对齐的单精度浮点数据传送指令.强行要求目标内存地址必须16字节对齐(整除)
2. movups(Move Unaligned Packed Single-Precision),允许内存地址不对齐

但编译器(MSVC/Rust)为了追求性能,默认生成movaps

踩坑场景:  
以mariana中的堆栈伪造为例,假设伪造了一个假栈帧,把伪造的RSP设置为了0x00007FFF12345608(尾数为 8，没有 16 字节对齐).一旦被伪造的系统api(如 RtlUserThreadStart或c标准库函数)内部执行了 `movaps [rsp+0x20],xmm6` cpu发现rsp+0x20的末尾是8不能被16整除.  
那么cpu的SSE的硬件电路会拒绝执行,抛出硬件级#GP通用保护异常,程序连捕获异常的机会都没有,直接闪退

解决方案:  
在编写伪造栈时,发起call指令之前的原始基准栈顶(rsp_base)物理上必须是16字节对齐的.之后,cpu的call指令物理上自动压入了8字节的返回地址(rsp_base-8,此时不能16字节对齐).之后,被调用的子函数prologue内部执行流sub rsp,0x28或push reg,rsp又变成16字节对齐.

## x64 影子空间（Shadow Space / Home Space）32 字节留空

这是导致堆栈覆盖、内存局部变量被莫名其妙篡改的坑

物理本质:
1. win64 abi中,前四个参数通过cpu寄存器传递(rcx,rbx,r8,r9).微软规定,即使没有4个参数,调用者caller也必须在call之前,在栈顶开辟32字节的影子空间.
2. 被调用的子函数在运行期间,如果需要把rcx里的参数临时写回内存,它默认会直接写进调用者留给他的影子空间中.

踩坑场景:  
子函数被编译时,编译器默认它的rsp上方有32字节的空地.如果伪造假栈时没有预留这32字节,子函数的写内存指令会强行覆盖后面的函数返回地址.

解决方案:  
一定记得预留32字节的影子空间

## `Rust #![no_std] 结构体 #[repr(C)] 内存重排坑`

Rust 编译器默认对结构体的内存布局拥有自由重排权（repr(Rust)）.为了减少 padding 内存浪费，Rust 会自动打乱你在 struct 里写的字段顺序

所有需要与 ASM 汇编、Windows 系统 API 或二进制 PE 内存比对的 Rust结构体，100% 必须加上 `#[repr(C)]` 或 #[repr(C, packed)]

## `#[repr(packed)] 引发的未对齐解引用 Unaligned Pointer Drop`坑

如果在 Rust 中为了强行匹配 PE 文件头（如 IMAGE_DOS_HEADER），给结构体加上了`#[repr(packed)]`（取消一切内存 Padding 对齐）：结构体内部的某个 u32 或 u64 字段，物理内存地址可能会落在一个奇数地址（如0x1001）上

踩坑场景:  
如果试图对一个未对齐结构体内部的字段创建引用
```rust
 #[repr(packed)]
    struct UnalignedHeader {
        flag: u8,
        target_addr: u64, // 物理地址落在了 0x1001 (未对齐!)
    }

    let header: UnalignedHeader = ...;
    // ❌ 物理大坑！创建了未对齐字段的引用！
    let addr_ref: &u64 = &header.target_addr;
```
win64下,直接解引用&u64这样未对齐指针,轻则导致cpu运行效率低下,重则在某些 strict-alignment 编译目标下直接引发UB崩溃

Rust 最新编译器会直接报错：reference to packed field is unaligned
