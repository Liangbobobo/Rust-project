核心演进方向一：Agent 客户端运行时闭环 (Rust)

  在客户端层面，需将现有的协议组件串联为可独立运行的业务闭环：
  #### 1. 落地 Win32 原生环境遥测采集 (src/sysinfo.rs)
  • Mythic 4.0 规范契约：
  在发送 CheckinMessage
  时，必须填充宿主机元数据：ips、os、user、host、pid、architecture、domain、i
  ntegrity_level。
  • 工程要求：
      • 杜绝派生外部子进程：严禁执行任何外部系统命令，纯粹通过原生 Win32 API
      采集。
      • 核心 API 映射：
          • 主机名：GetComputerNameExW
          • 用户名与所属域：GetUserNameExW / GetUserNameW
          • 进程 PID：GetCurrentProcessId
          • 系统架构：GetNativeSystemInfo
          • 网卡 IP 列表：GetAdaptersAddresses
          • 权限级别：通过 OpenProcessToken 与 GetTokenInformation 检索
          TokenIntegrityLevel，映射为 Mythic 标准数字级别（1: Low, 2: Medium,
          3: High, 4: SYSTEM）。
      • 零堆分配：数据直接写入定长栈数组缓冲区，格式化为 &str 切片。
  ──────
  #### 2. 构建会话生命周期与心跳状态机 (src/engine.rs)
  • Mythic 4.0 规范契约：
  驱动 Agent 完成从冷启动上线到常态轮询的完整状态迁移。
  • 状态机模型：
    [Unregistered] --(发送 Checkin 报文)--> [Registered: 锁定并保存 Callback
  UUID]
                                                      │
                                                      ▼
    [Sleeping: Jitter 动态休眠] <--(回执 ACK)-- [Active: 发送 get_tasking
  捎带回执]

  • 核心职责：
      • 维持当前活跃凭据：启动时持预设的
      PayloadUUID，上线成功后切换为服务端分配的 CallbackUUID。
      • 心跳调度：结合 DEFAULT_SLEEP_INTERVAL 与 DEFAULT_SLEEP_JITTER
      执行动态时间浮动。
      • 顺风车捎带（Piggybacking）：在发起 get_tasking
      心跳请求的同时，将已执行完毕的任务回执（responses）或文件传输分片一次性
      同步回传。

  ──────
  #### 3. 建立指令路由器与基础内建命令 (src/commands/)

  • Mythic 4.0 规范契约：
  服务端下发的任务由 command 标识。Agent 需要建立分发映射，解析参数并产生
  TaskResponseItem。
  • 首批核心指令集：
      • sleep：动态调整休眠周期与抖动率。
      • exit：安全析构会话并擦除内存密钥。
      • cd / ls / pwd：对接现有 FileBrowserResponse 上报文件目录树与状态。
      • download / upload：驱动现有的 TransferSession
      完成纯字节偏移文件双向传输。

  ──────
  ### 核心演进方向二：Mythic 服务端容器适配 (Python)

  根据 Mythic 4.0 架构，任何 Agent 要在 Mythic
  控制台中被操作员使用，必须提供一个基于 mythic_container 的独立服务容器：

  #### 1. 定义 PayloadType 基础元数据

  创建 agent_service/builder.py，继承 PayloadType 类声明 Agent 特性：

  • name = "wisconsin"
  • supported_os = [SupportedOS.Windows]
  • c2_profiles = ["http"]
  • translation_container = None（原生采用官方标准 JSON 与
  aes256_hmac，无需自定义格式翻译容器）

  #### 2. 绑定 UI Hooking 与命令声明
  在容器中为每个支持的指令定义参数规范与 UI 交互特征：
  • 目录浏览声明 supported_ui_features = ["file_browser:list",
  "file_browser:remove"]，使前端界面自动渲染文件树。
  • 进程列表声明 supported_ui_features =
  ["process_browser:list"]，使前端自动关联并渲染交互式进程拓扑。

  #### 3. 编排编译流水线 (build 函数)

  在容器内接收 Web 端生成的参数（C2 URL、休眠时间、AESPSK
  密钥），通过预设宏或编译期常量替换，触发 cargo build --release 编译出最终
  PE 文件。
  ──────
  ### 推荐落地顺序
  建议优先完成 客户端运行时闭环（sysinfo.rs → engine.rs），在本地通过 Rust
  单元/集成测试打通从“环境收集 → 上线注册 →
  心跳轮询”的完整逻辑流；随后再编写服务端 Docker 适配容器，完成与 Mythic Web
  控制台的对接。
