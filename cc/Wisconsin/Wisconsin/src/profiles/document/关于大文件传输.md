在无标准库 (no_std + alloc) 且严重依赖内存隐蔽的 Red Team / C2项目中，大文件（如几百 MB 到 GB 级）传输如果一次性加载到堆中（例如`Vec<u8>`），不仅会触发 Windows 10/11 Segment Heap 的严重高频堆分配抖动（触发ETW-Ti 告警），还会极易导致内存不足崩溃或内存残留（Heap Remanence）

在设计上通过以下 4 个核心维度 彻底避免堆分配：

```text
           [大文件 / 磁盘 / 内存流]
                      │
     1. 流式分块 (Stream Chunking)
                      ▼
   ┌─────────────────────────────────────┐
   │ Caller 栈帧固定缓冲区 [u8; 2048]     │ (零堆分配)
   └─────────────────────────────────────┘
                      │
     2. 零拷贝 Base64 借用切片 (&'a str)
                      ▼
   ┌─────────────────────────────────────┐
   │ FileChunkPayload / TaskResponseItem │ (仅占胖指针 16B)
   └─────────────────────────────────────┘
                      │
     3. 外部提供工作区 (Caller-Provided Buffer)
                      ▼
   ┌─────────────────────────────────────┐
   │ HttpProfile::build_file_chunk_payload
   │ In-place 原地 AES-CBC 加密 + Base64  │ (解密/加密复用栈缓冲区)
   └─────────────────────────────────────┘
                      │
     4. 物理擦除 & 环形复用 (Zeroize & Reuse)
                      ▼
            [下发下一分片 / 循环往复]
```

详细技术要点：

1. 流式固定分片（Stream Chunking & Budget Constrained）

   - 不将大文件一次性读取到内存中，而是按照 crypto.rs
     约束的单个分片净载荷预算（约 2000~2048 字节）在 Caller 栈帧
     上开辟固定大小的缓冲区（如 let mut chunk_buf = [0u8; 2048]）。
   - 每次只从文件句柄或读取流中 read 填充这 2048 字节。

2. 零拷贝借用切片 (&'a str / &'a `[u8]`)

   - 将分块二进制数据转为 Base64 编码时，Base64
     字符串直接写入栈上的临时字符数组，FileChunkPayload 和 TaskResponseItem
     仅持有对该栈缓冲区的 &'a str 切片引用。
   - 整个结构体在 64 位系统上仅占 16 字节胖指针（Pointer +
     Length），不发生任何 malloc/alloc 动态内存申请。

3. Caller-Provided Buffer（调用者提供工作区）

   - HttpProfile 的打包解包逻辑全线要求调用者传入 raw_buf: &mut `[u8]` 和
     out_b64: &mut `[u8]`（即全局复用或栈上预分配的暂存区）。
   - AES-CBC 加密、PKCS#7 填充、HMAC 计算及最终 Base64
     编码均在这些预置缓冲区中原地（In-Place）完成。

4. 即用即清与内存环形复用 (Zeroization & Cyclic Buffer)

   - 发送完单分片报文后，立即调用 zeroize_slice
     洗白栈缓冲区，并重用该缓冲区处理下一个分片。
   - 这种方式使得无论传输 1 MB 还是 10 GB 的大文件，Agent 进程的 RAM
     堆内存占用始终恒定在几 KB 左右。
