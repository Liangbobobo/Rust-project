


## 与浏览器 HTTP 通信的区别

浏览器的 HTTP 通信是标准的 Web 客户端请求模型（短连接、高并发、重 Header、同步/异步 Promises），而这里的 C2 (Command & Control)通信具有完全不同的安全威胁模型与设计目标

| 对比维度 | 浏览器 HTTP 通信 | C2 隐蔽 HTTP Profile 通信 |
|---|---|---|
| 核心目标 | 快速加载网页、吞吐量最大化、标准兼容 | 绝对隐蔽性、0 内存残留、防 EDR / WAF 流量检测 |
| 内存分配 | 随意向堆申请大量空间、使用垃圾回收 / 引用计数 | 0 动态堆分配，杜绝 Windows Segment Heap 抖动告警 |
| 安全清除 | 敏感数据交由 OS 管理，生命周期结束后等待 GC | RAII 强制物理擦除（`zeroize_slice`），离开作用域逐字节清零 |
| 数据载荷 | 明文 / TLS 标准加密、包含标准 User-Agent / Cookie 等 | 应用层强加密二次封包（AES-CBC + HMAC-SHA256 + Base64） |
| 传输模式 | 请求-即时响应（Request-Response） | 异步心跳拉取（Pull / Polling），单次心跳严格受限于 2KB 净预算 |

## 关于并发

主通信管道不需要并发，但底层任务执行支持并发

**1. 主通信管道（C2 链路）是单线程反向心跳轮询（Single-threaded Polling）**

- 为什么不能并发发包？
  如果 Agent 同时建立 10 个 TCP/HTTP 连接向 C2 服务器发包，这种并发突发流量在企业网关 NDR / WAF / EDR 看来是极其明显的木马行为特征。

- 隐蔽原则：
  C2 流量必须保持“低频、单线程、随机抖动 Interval”出站，伪装成普通用户偶然刷新网页的行为。

**2. 任务执行层与通信层的解耦（并发处理）**

- 主通信线程负责拉取任务（get_tasking）。若拉到耗时极长的数据采集或扫描任务，Agent 会调用 `MythicTaskRef::to_owned()` 将其转为拥有所有权的 `MythicTask`，然后通过 `std::thread::spawn` 或 Worker 线程池移交给后台并发执行。

- 主通信线程则立刻恢复 Sleep 心跳，并发任务在后台异步运行，结果分阶段追加回传输队列，从而既保证了 C2 链路的单线程隐蔽性，又实现了任务的并发执行
