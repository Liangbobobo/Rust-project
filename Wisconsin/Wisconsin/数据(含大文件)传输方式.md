## 大文件传输和HTTP-Keep-Alive/Live状态长连接网络传输调度器(尚未实现)

1. 纯栈流式切片
2. http-live模式，避免多次发送报文头
3. 每次传输64kb大小数据，但是又想实现动态大小，避免出现固定大小的流量特征
4. 随着每次心跳包发送数据，但又想将传输任务作为后台执行，不耽误其他心跳包接收服务端指令
5. 没有断点续传的容错性和socket 卡死与进程死锁风险的解决方案


**设计目标 1：流式切片**

- 已实现 `FileChunkPayload<'a>` 和 `TaskResponseItem::new_file_chunk()`：支持将任意大文件切割成分片报文，包含 `chunk_num`（当前片）、`total_chunks`（总片数）、`file_id` 和 Base64 编码的 `chunk_data`。
- 已实现 `build_file_chunk_payload()`：可以将单片数据在栈内存中完成 AES-CBC-HMAC 加密并打成 Base64，做到 100% 零堆分配。

**设计目标 2：http-live 模式，避免多次发送报文头**

- 不要维持长连接 Stream POST（Chunked Transfer Encoding）。因为持续不关闭的 HTTP 请求会使套接字长期处于 `ESTABLISHED` 状态，极易在 Windows `netstat` / EDR 进程网络连接列表中暴露。
- 使用 HTTP Keep-Alive 复用 TCP 管道，但每次传输依然使用标准的短 HTTP POST 报文。这样既规避了频繁 TLS 握手的 CPU/时间开销，又符合正常 Web 浏览器的连接复用行为。
- 目前只有 profiles（即加密与序列化协议 Profile），缺失真正的网络 Socket / WinHTTP 传输循环。

**设计目标 3：每次传输 64KB 大小数据，但实现动态大小，避免固定大小的流量特征**

- 固定大小（如每次刚好 64,000 字节）会在网络防火墙 / NDR / 流量分析系统（如 Suricata / Zeek）中产生极其明显的数据包长度直方图特征。
- 采用正态 / 高斯分布抖动（Gaussian Jitter），计算动态尺寸：

```text
ChunkSize = BaseSize(64KB) ± Jitter(16KB) ⟹ 48KB ∼ 80KB
```

**设计目标 4：随着每次心跳包发送数据，但传输任务作为后台执行，不耽误其他心跳包接收服务端指令**

- 未实现每次心跳自动 Seek 磁盘文件并交替发送的后台调度器（Task Scheduler）。
- Mythic 协议的设计天然支持 Piggybacking（顺风车复用）。代理 Agent 在每次心跳触发时，构造一个 `PostResponseMessage`（回执消息），这个消息内部包含一个数组：

```text
responses: &[TaskResponseItem]
```

其中包含：

- `TaskResponseItem 1`：GetTasking / 心跳查询（拉取操作员下发的新命令）。
- `TaskResponseItem 2`：`FileChunkPayload`（带上后台文件传输队列中当前读取的 1 片 64KB 动态数据）。

效果：

1. 零额外 HTTP 请求：传输任务完全搭上心跳包的“顺风车”，没有产生任何额外的 HTTP 连接。
2. 不耽误接收新指令：服务端在接收这一片文件的同时，回包依然会下发新的 C2 指令（如 `whoami`、`sleep`）。
3. 完美的离散化后台运行：Agent 内部维持一个简单的 `TaskQueue` 状态机，每次心跳只读 1 片，读完置零退出，主线程绝不阻塞，同时完美实现多任务并行。

- 每次心跳进行 `Open -> Seek -> Read -> Close` 存在以下红队隐患：
  - NTFS 访问时间戳更新（MFT Timestamp Drift）：频繁打开大文件进行 Read 会更新文件的 `LastAccessTime`，极易被 EDR 的文件系统过滤器驱动（Minifilter Driver，如 `fltmgr.sys`）通过 MFT 变更事件捕获。
  - 句柄打开 / 关闭事件（Handle Creation Thrashing）：高频打开 / 关闭敏感文件句柄会被 `Sysmon Event ID 11` 或 EDR 的 `ObRegisterCallbacks` 钩子记录。
- 优化方案：只读共享与时间戳冻结。在 `CreateFileW` 或 `std::fs::File::open` 时，必须显式指定：

```text
FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE
```

并设置：

```text
FILE_FLAG_SEQUENTIAL_SCAN
```

- 内存映射只读视口（`VirtualAlloc` / `MapViewOfFile` + Memory Protection）替代常规 Read：对于特别敏感的大文件，可一次性建立 `PAGE_READONLY` 的 Section 映射，或者通过 `SetFileTime` 显式冻结 `LastAccessTime`，规避 MFT 时间戳漂移痕迹。

> 但是直接去掉异步，等大文件传输完毕不就解决这样的问题了吗？这样会导致心跳包不能执行其他指令的缺点外，还有其他劣势吗？(不能使用这种方式)

一次性发完大文件除了阻塞主线程外,还有其他严重劣势
1. 短时间的大量hppt post请求很容易被发现
2. 文件系统 IO 吞吐量峰值触发 EDR
3. while 循环中无休止地进行 Read -> AES 加密 -> Base64 编码 -> Socket Send，会导致当前cpu占用率飙升
4. 在离散心跳模式下：若发现蓝队开始抓包，操作员可以立即下发 sleep 86400（休眠一天）或exit（自毁）

**设计目标 5：纯栈操作**

- 为了支持 64KB ± Jitter 的动态分片而在栈上直接分配：

```rust
let mut buf = [0u8; 81920];
```

约 80KB。Windows 默认线程栈 Guard Page 为 4KB。当局部变量单次超过 4KB 时，LLVM 编译器会强制插入 `__chkstk` 调用。若 EDR Hook 了 `__chkstk` 或在栈回溯（Stack Walk）中检测到异常的深栈帧（Unusual Large Frame Pointer），会触发异常告警。
- 栈擦除不彻底（Spare Stack Remanence）：若仅擦除实际 Read 的字节，未初始化的栈空间在退栈后可能留有上一次调用的指针或残余敏感数据。

**优化方案：**

- 动态 StackArena 预先隔离：复用项目已有的 `models.rs` 中的 `StackArena`，在进入心跳主逻辑前，按最大上限（如 80KB）声明一块：

```rust
StackArena<81920>
```

- 使用 volatile 全量强制刷零：必须确保在退栈前，擦除的是整块预留缓冲区 `0..CAP`，而不仅仅是 `0..offset`。代码中采用项目已实现的裸指针 `core::ptr::write_volatile`，彻底杜绝编译器死码消除（Dead Store Elimination, DSE）导致的刷零被优化问题。

**综合**

当前方案结合 **“Piggybacking 顺风车复用 + 高斯动态分片 + 句柄即用即销 / 时间戳冻结 + 栈全量擦除”**，能够兼顾极致的 OPSEC 隐蔽性与长时传输的稳定性。
